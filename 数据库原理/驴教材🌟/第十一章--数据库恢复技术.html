第十一章 数据库恢复技术

确保数据安全与系统可靠性的核心技术

11.1 事务的基本概念 重要

1. 事务 (Transaction) 重要

事务是用户定义的一个数据库操作序列，这些操作要么**全部执行成功**，要么**全部不执行（回滚）**，它是一个不可分割的逻辑工作单位。

想象一下银行转账：从A账户扣钱，再给B账户加钱。这两个动作必须作为一个整体成功或失败。如果只扣了A的钱，没给B加，那数据库就"乱了套"。事务就是为了保证这种"要么全做、要么全不做"的完整性。

  • 事务与程序的关系： 一个程序可以包含多个事务，但一个程序通常包含多个事务。事务是数据库恢复和并发控制的最基本单位。

定义事务的方式：

  • 显式定义方式：
    SQL Code Example: 显式事务提交
    BEGIN TRANSACTION;     -- 执行一系列SQL语句 (例如：更新A账户余额)     -- Execute more SQL statements (e.g., update B account balance) COMMIT; /* 事务正常结束，所有修改永久保存 */

    当所有操作都顺利完成，使用COMMIT命令将事务中对数据库的所有修改永久保存到磁盘上。

  • 隐式方式（异常终止与回滚）：
    SQL Code Example: 隐式事务回滚
    BEGIN TRANSACTION;     -- SQL statement 1     -- SQL statement 2 (Assume a fault occurs here, transaction is terminated) ROLLBACK; /* 事务异常终止，所有修改撤销 */

    如果事务在执行过程中遇到问题或被强制中断，数据库系统会自动或通过ROLLBACK命令撤销该事务已经进行的所有修改，使数据库回到事务开始前的状态。

2. 事务的ACID特性 必考

ACID是确保数据库事务可靠执行的四个核心特性：

  • 原子性 (Atomicity)： 事务是数据库的逻辑工作单位，它包含的所有操作要么全部成功，要么全部失败回滚，不会出现部分执行的情况。

    就像化学中的原子，不可再分。一个事务要么完整地发生，要么完全不发生。比如银行转账，取钱和存钱必须同时成功，否则就当没发生过。

  • 一致性 (Consistency)： 事务执行后，数据库必须从一个合法（一致）的状态转变为另一个合法（一致）的状态。一致性状态是指数据库满足所有预定义的完整性约束（如主键唯一、外键引用有效、余额非负等）。

    你可以把它理解为数据库的"健康状态"。事务开始时是健康的，结束时也必须是健康的。如果转账中途失败，钱既没到账也没退回，就是不健康的（不一致）状态。

    银行转账事务的一致性示例

    SQL Code Example: 确保一致性的转账操作
    BEGIN TRANSACTION; UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 'A123'; UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 'B456'; COMMIT;

    这两个UPDATE语句必须作为一个原子操作来执行，以确保转账前后总金额不变，维持数据库的一致性。

  • 隔离性 (Isolation)： 多个并发执行的事务互不干扰，每个事务的执行仿佛是系统中的唯一事务，即使它们同时读写相同的数据。

    想象多个人同时在一个文档上编辑，但每个人看到的都是自己修改前的版本，或者只看到已经保存的最终版本，不会看到别人修改到一半的"脏数据"。这就像数据库给每个事务开了一个"独立的工作间"。

    并发事务隔离性示例

    SQL Code Example: 并发事务 (理论隔离)
    -- 事务 T1 BEGIN TRANSACTION; UPDATE Products SET Stock = Stock - 10 WHERE ProductID = 'P001'; -- ... T1 continues operations or waits ... COMMIT; -- 事务 T2 (executes concurrently) BEGIN TRANSACTION; SELECT Stock FROM Products WHERE ProductID = 'P001'; -- ... T2 continues operations or waits ... COMMIT;

    在理想隔离下，T2在读取P001库存时，要么读取到T1修改前的库存（如果T1未提交），要么读取到T1修改后的库存（如果T1已提交），不会读取到T1修改一半的中间状态。

  • 持续性 (Durability)： 一旦事务成功提交，它对数据库中数据的修改就是永久性的，即使系统发生故障也不会丢失。

    好比你在电脑上保存了一个文档。一旦你点击"保存"，即使电脑突然断电，当你下次开机时，文档依然是保存时的样子，不会丢失。

事务ACID特性总结
特性 含义 破坏后果 保障机制
原子性 事务是不可分割的整体，要么全做，要么全不做 部分操作成功导致数据不一致 事务回滚(UNDO)
一致性 事务前后数据库都处于有效状态 违反完整性约束，数据无效 应用程序逻辑+数据库约束
隔离性 并发事务互不干扰 脏读、不可重复读、幻读 锁机制/MVCC
持续性 提交的事务永久保存 已提交操作丢失 日志重做(REDO)

破坏事务ACID特性的因素： 了解

主要有两个方面会导致ACID特性被破坏：

  • 多个事务并行运行时，操作交叉执行： 如果数据库系统没有妥善处理并发访问，就可能出现数据读写冲突，导致一致性和隔离性被破坏。
  • 事务在运行过程中被强行停止： 任何非正常的程序中断（如断电、软件崩溃）都可能导致事务无法完成，进而破坏原子性和一致性。

11.2 数据库恢复概述 重要

故障的不可避免性 了解

在数据库系统长时间运行过程中，硬件故障（如磁盘损坏）、软件错误（如操作系统或数据库系统Bug）、操作员失误（如误删数据）以及恶意破坏（如病毒攻击）等都可能发生，导致数据丢失、损坏或处于不一致状态。

数据库的恢复 了解

数据库的恢复是指当数据库系统发生故障时，将数据库从不正确的状态（可能数据损坏或丢失）恢复到故障发生前某个正确状态的过程。这是数据库管理系统（DBMS）的一项核心功能。

恢复的基本原理是**冗余**：通过在系统别处存储额外的数据副本（例如备份），在原数据损坏时利用这些副本重建数据。

11.3 故障的种类 重要

1. 事务内部的故障 重要

指单个事务在执行过程中，因程序逻辑错误、数据不符合约束、或并发冲突（如死锁）等原因，未能正常完成就被终止。这种故障仅影响当前事务，通常通过事务的**回滚 (UNDO)** 操作来撤销该事务的所有修改。

举个例子，你的程序尝试把一个负数作为年龄存入数据库，这违反了年龄必须大于0的规则。数据库就会强制终止这个事务，并撤销之前所有相关的修改。

2. 系统故障 (软故障) 重要

指造成整个系统突然停止运行的故障，例如操作系统崩溃、数据库管理系统软件自身错误或系统断电等。这类故障会导致内存中的数据库缓冲区内容丢失，所有正在执行的事务都被中断。

可以理解为电脑突然死机或断电。数据库本身可能没坏，但内存里的数据没了，有些操作做到一半就停了，导致数据库处于"半成品"状态。

3. 介质故障 (硬故障) 重要

这是最严重的故障类型，通常是由于存储介质（如硬盘）损坏导致的。这类故障会直接**破坏数据库文件或部分数据**，导致数据永久丢失。

这就像你的硬盘彻底坏了，上面的数据都读不出来了。这种故障的影响范围最大，恢复起来也最复杂。

数据库故障类型对比
故障类型 发生原因 影响范围 恢复难度 恢复方法
事务内部故障 程序逻辑错误、死锁、违反约束 单个事务 简单 事务回滚(UNDO)
系统故障(软故障) 断电、操作系统崩溃、DBMS错误 内存数据丢失 中等 UNDO未提交事务 + REDO已提交事务

11.4 恢复的实现技术 重要

数据库恢复的核心在于建立冗余数据，并在故障发生时利用这些冗余数据来重建或修正数据库。主要的冗余数据建立技术包括数据转储和登记日志文件。

11.4.1 数据转储 (Dump) 重要

转储是数据库管理员定期将整个数据库或其部分复制到备用存储介质（如磁带、另一个磁盘）上，以创建一份**后备副本（backup）**或**备份**的过程。

这就像给你的重要文件定期做个全盘备份，以防万一。当原数据损坏时，这份备份就是你的"救命稻草"。

转储方法： 了解

  • **静态转储 (Static Dump) 与动态转储 (Dynamic Dump)：**
    • 静态转储：

      在数据库系统完全停止运行（没有事务执行）时进行的备份。好处是备份数据一定是一致的；坏处是数据库在备份期间不能用。

    • 动态转储：

      在数据库系统正常运行、有事务并发执行时进行的备份。好处是不影响系统可用性；坏处是备份数据可能不一致（因为它可能包含正在进行但未提交的事务数据），所以必须配合日志文件才能用于恢复。

  • **海量转储 (Full Dump) 与增量转储 (Incremental Dump)：**
    • 海量转储：

      每次都备份整个数据库。优点是恢复简单快捷；缺点是耗时耗空间，尤其对于大型数据库。

    • 增量转储：

      只备份自上次任何类型转储（海量或增量）后发生变化的数据。优点是节省时间和空间；缺点是恢复过程相对复杂，需要先恢复最近的海量备份，再逐个应用后续的增量备份。

数据转储方法对比
分类维度 类型 优点 缺点 适用场景
系统状态 静态转储 数据一致性好 需要停机维护 小型系统、维护窗口
动态转储 无需停机 需配合日志使用 24/7运行系统
备份范围 海量转储 恢复简单快速 存储空间大、耗时长 首次备份、定期全量备份
增量转储 备份快速、空间小 恢复过程复杂 日常频繁备份

11.4.2 登记日志文件 (Logging) 重要

日志文件 (log file) 是一种特殊的文件，它顺序记录了数据库中所有事务对数据的更新操作。每条日志记录都包含足够的细节（如事务ID、操作类型、修改的对象、修改前的值、修改后的值），以便在需要时撤销或重做操作。

日志文件就像数据库操作的"流水账"，详细记录了每次数据变化的来龙去脉，是恢复操作的"证据链"。

日志记录示例
-- 事务T1开始 START TRANSACTION T1; -- T1更新账户A UPDATE Accounts SET Balance = 500 WHERE ID = 'A'; -- 日志记录: [T1, 账户A, 原值:1000, 新值:500] -- T1更新账户B UPDATE Accounts SET Balance = 1500 WHERE ID = 'B'; -- 日志记录: [T1, 账户B, 原值:1000, 新值:1500] -- T1提交 COMMIT T1; -- 日志记录: [T1 COMMIT]

日志文件的作用： 了解

日志文件是数据库恢复的"基石"，其主要作用有：

  • **事务故障恢复：** 用于撤销未完成事务对数据库的修改。
  • **系统故障恢复：** 用于撤销未完成事务和重做已提交事务。
  • **协助介质故障恢复：** 在装载备份后，利用日志文件将数据库恢复到故障发生前的最新状态。

登记日志文件的两条原则： 必考

  • **登记的次序严格按并发事务执行的时间次序。**
  • **必须先写日志文件，后写数据库。**

    这条原则至关重要！它要求在数据实际被修改并写入磁盘上的数据库文件之前，代表该修改的日志记录必须首先被写入并确保安全地存储在日志文件中。这样一来，即使在数据写入数据库文件前系统突然崩溃，日志中也会有完整的操作记录，系统就能根据日志来恢复数据。如果先改了数据但日志还没写好就崩溃了，那么这部分修改就无从恢复了。

日志记录黄金原则

日志记录必须先于数据写入磁盘！

这个原则确保了在任何故障情况下，数据库都能根据日志记录进行恢复操作。如果违反此原则，可能会导致已提交的事务修改丢失，或者未提交的事务修改无法撤销。

11.5 恢复策略 了解

1. 事务故障的恢复 了解

当一个事务因内部错误或系统强制终止而失败时，恢复子系统会利用日志文件对该事务已做的所有修改执行**撤销 (UNDO)** 操作。这意味着将所有受影响的数据项恢复到它们在事务开始之前的值，确保事务的原子性。

就像玩游戏时操作失误，系统会让你"回档"，回到你犯错之前的状态，你之前的操作都作废了。

2. 系统故障的恢复 了解

系统故障（如断电）发生时，内存中的数据会丢失，所有正在运行的事务都会中断。恢复策略需要执行两类操作：

  • **撤销 (UNDO) 操作：** 对所有在故障发生时**尚未完成**的事务，撤销它们已对数据库进行的任何修改。
  • **重做 (REDO) 操作：** 对所有在故障发生前已经**提交成功**的事务，但其修改可能还停留在内存缓冲区未写入磁盘的，重新执行这些修改，确保它们被持久化到数据库中。

这就像电脑突然重启。重启后，数据库会检查日志：对于那些"没来得及完成"的操作，一律撤销；对于那些"已经完成但还没存到硬盘"的操作，会重新执行一遍，确保数据都存好。

系统故障恢复流程
-- 系统重启后执行恢复 FOREACH transaction IN log     IF transaction has COMMIT record BUT data not on disk         REDO(transaction) // 重做已提交事务     ELSE IF transaction has no COMMIT record         UNDO(transaction) // 撤销未完成事务     END IF END FOREACH

3. 介质故障的恢复 了解

当存储介质损坏导致数据库文件受损时，这是最复杂的恢复情况。恢复过程通常由数据库管理员手动启动，并涉及以下步骤：

  • **装入最新的数据库备份：** 将最近的（通常是海量转储或完整备份）数据库副本重新加载到磁盘上。这会将数据库恢复到备份时的状态。
  • **装入相关日志文件并重做事务：** 接着，加载从备份点到故障发生期间的所有日志文件。通过正向扫描日志，识别并**重做 (REDO)** 所有在该时间段内已成功提交的事务，将这些修改应用到恢复的备份上，从而使数据库达到故障发生前的最新一致状态。

这就像你的手机坏了，你只能先用上次备份恢复（回到过去某个时间点），然后把你备份之后到手机坏掉之前所有重要的操作（比如新拍的照片、新发的微博）再"重演"一遍，才能恢复到手机坏掉之前的最新状态。

11.6 具有检查点的恢复技术 了解

问题的提出 了解

传统的恢复策略在系统故障时，需要从日志文件头开始扫描，并对所有已提交事务进行重做。这会消耗大量时间和计算资源，尤其对于大型、繁忙的数据库。为了解决这个问题，引入了检查点技术。

1. 检查点记录与重新开始文件 了解

检查点 (Checkpoint) 技术的核心是：系统会周期性地创建一个"检查点记录"并写入日志文件。这个记录包含了当前时刻所有活跃事务的列表，以及它们在日志文件中的最新记录地址。

同时，系统会维护一个"重新开始文件"，专门记录最近一个检查点记录在日志文件中的地址。这样，在发生系统故障需要恢复时，可以直接从这个最近的检查点开始扫描日志，而不是从日志文件的最开头，大大缩短了恢复时间，提高了效率。

2. 恢复子系统的恢复策略 了解

在系统故障发生时，恢复子系统不再需要从头扫描日志，而是从"重新开始文件"找到的最近检查点开始。它会根据日志记录判断哪些事务需要被**撤销 (UNDO)**（在故障点时尚未完成的事务），以及哪些事务需要被**重做 (REDO)**（在检查点之后提交但其修改可能未写入磁盘的事务）。而那些在检查点之前就已经提交的事务，系统认为其修改已经持久化到磁盘，因此在恢复时通常不需要再次重做，进一步提高了恢复速度。

11.7 数据库镜像 (Mirror) 了解

概述与工作原理 了解

数据库镜像是一种高可用性解决方案，用于预防最严重的介质故障。其原理是DBMS自动地将整个数据库或关键数据实时复制到另一个独立的存储介质（镜像磁盘）上。每当主数据库发生更新时，这些修改也会自动同步到镜像副本，确保两者的数据一致性。

就像给你的数据库找了个"双胞胎"，一个在工作，另一个实时同步，随时可以顶替，以防万一。

主数据库
镜像数据库

数据库镜像的用途 了解

  • **提高可用性：** 当主数据库因介质故障无法访问时，系统可以立即切换到镜像副本，继续提供服务，无需漫长的恢复过程。
  • **支持并发操作：** 在没有故障时，镜像副本也可以用于只读查询，减轻主数据库的负载，提高系统的并发处理能力。
