第十二章 并发控制

协调多用户操作，确保数据库数据正确性

12.1 并发控制概述 必考

多用户数据库系统与并发操作 重要

在多用户数据库系统中，许多用户可能同时访问和操作数据库。例如，飞机订票系统、银行交易系统、网上购物系统等，在同一时刻可能有成千上万个事务并发运行。

想象一下，一个热门商品的库存只剩下最后一件，好几个人同时点击"购买"。如果没有并发控制，就可能出现问题。

多事务执行方式： 了解

  • (1) 事务串行执行 (Serial Execution)：

    在任意时刻只有一个事务在运行，其他事务必须等待当前事务结束后才能开始。这种方式能保证数据一致性，但效率极低，不能充分利用系统资源。

    串行执行示意图

    T1
    Op A
    Op B
    T2
    Op X
    Op Y
    T3
    Op M

    T1执行完所有操作后，T2才开始，T2执行完T3才开始，以此类推。

  • (2) 交叉并发方式 (Interleaved Concurrency)：

    在单处理机系统中，多个并发事务的操作轮流交叉运行。虽然不是真正的同时执行，但通过快速切换（CPU调度），可以减少处理器的空闲时间，提高系统效率。

    交叉并发执行示意图

    T1
    R(A)
    W(A)
    R(B)
    T2
    R(A)
    W(A)
    Commit

    T1读取A，然后CPU切换到T2，T2也读取A并修改，再切换回T1。操作在时间上交错进行。

  • (3) 同时并发方式 (Simultaneous Concurrency)：

    在多处理机系统中，每个处理器可以运行一个事务，从而实现多个事务真正的并行运行。这种方式能最大化利用硬件资源，但需要更复杂的并发控制机制。

    同时并发执行示意图

    CPU 1 (T1)
    R(A)
    W(A)
    CPU 2 (T2)
    R(X)
    W(Y)

    T1和T2在不同的CPU上同时执行，互不等待。

事务并发执行带来的数据不一致性 必考

并发操作虽然提高了系统效率，但也可能导致多个事务同时存取或修改同一数据，从而破坏事务的隔离性，进而导致数据库数据的不一致性。数据库管理系统必须提供并发控制机制来解决这些问题。

并发控制机制是衡量一个数据库管理系统性能的重要标志之一。

并发操作可能导致的不一致性问题类型：

以下是几种经典的，由于并发操作而破坏事务隔离性，导致数据不一致性的情况。记住它们的定义和产生原因非常重要。

  • 1. 丢失修改 (Lost Update)：

    两个事务T1和T2读入同一数据并修改，T2的提交结果破坏了T1提交的结果，导致T1的修改被丢失。

    就像两个人同时编辑一份文档，甲修改后保存，但乙并不知道甲的修改，也修改了同一部分并保存，结果甲的修改就被乙覆盖了，永久丢失。

    丢失修改示例：飞机订票系统

    初始状态：某航班机票余额 A = 16
    事务T1 (甲售票点) 读取 A = 16
    事务T2 (乙售票点) 读取 A = 16
    T1 卖出一张票，计算 A = 15，并写回数据库 (A = 15)
    T2 卖出一张票，计算 A = 15 (基于它读到的旧值)，并写回数据库 (A = 15)
    结果： 实际卖出两张票，但数据库余额只减少了1张 (T1的修改被T2覆盖丢失)。
    T1
    R(A)=16
    A←A-1
    W(A)=15
    T2
    R(A)=16
    A←A-1
    W(A)=15
    T1的修改被T2覆盖！
  • 2. 脏读 (Dirty Read)：

    指一个事务T1修改了某一数据，并将其写回磁盘（但尚未提交），而另一个事务T2读取了同一数据。随后，T1由于某种原因被撤销（回滚），这时T1已修改过的数据恢复原值，导致T2读到的数据是"脏"数据，即不正确的数据。

    就像你读了一本还没写完的书的某个章节，结果作者觉得不满，把那章删了。你读到的内容就是"脏"的，因为最后它根本不存在。

    脏读示例：商品价格调整

    初始状态：商品C价格 = 100
    事务T1 修改C的价格为 200 (W(C)=200)，但**未提交**
    事务T2 读取 C = 200
    T1 因为某种原因回滚 (ROLLBACK)，C的价格恢复为 100
    结果： T2 读到的 C 价格是 200，但数据库中实际价格已恢复为 100。T2读到了"脏数据"。
    T1
    R(C)=100
    C←C*2
    W(C)=200
    ROLLBACK
    T2
    R(C)=200
    T2读到T1未提交的数据，T1回滚后T2的数据就"脏了"！
  • 3. 不可重复读 (Non-Repeatable Read)：

    指事务T1读取数据后，事务T2执行**更新**操作（修改或删除）同一数据，使T1无法再现前一次读取结果。即事务T1在两次读取同一数据时，得到了不同的值。

    你第一次看某篇文章，文章说"XX有100个优点"。过了一会儿你再看同一篇文章，它更新了，变成了"XX只有50个优点"。你两次读到的不一样，这就是不可重复读。

    不可重复读示例：数据验证

    初始状态：A=50, B=100
    事务T1 第一次读取 A=50, B=100，计算和为150
    事务T2 读取 B=100，修改B为 200，并提交
    T1 再次读取 A=50, B=200，计算和为250
    结果： T1 两次读取B的值不一致，第一次是100，第二次是200。
    T1
    R(A)=50
    R(B)=100
    Sum=150
    R(A)=50
    R(B)=200
    Sum=250
    T2
    R(B)=100
    B←B*2
    W(B)=200
    Commit
    T1两次读取同一数据B，结果不一致！
  • 4. 幻读 (Phantom Read)： 了解

    指事务T1按一定条件从数据库中读取某些数据记录后，事务T2执行**插入或删除**操作，使T1无法再现前一次读取结果。

    • 插入幻影： T1 第一次读取时没有满足某些条件的数据，T2 插入了满足条件的新数据。T1 再次按相同条件查询，发现"多了一些"记录。
    • 删除幻影： T1 第一次读取时有满足条件的数据，T2 删除了其中部分记录。T1 再次按相同条件查询，发现"少了一些"记录。

    你数了一下房间里有10个人。过了一会儿，另一个人又带进来了2个人，或者带走了2个人。你再数，人数就不对了，但你感觉像"幻影"一样，多出来或少掉的这些人是在你眼皮子底下变化的。

    幻读示例：用户注册系统

    事务T1查询用户表："SELECT * FROM users WHERE age > 18" → 返回10条记录

    事务T2插入一个新用户：INSERT INTO users (name, age) VALUES ('新用户', 20)

    事务T1再次执行相同查询："SELECT * FROM users WHERE age > 18" → 返回11条记录

    T1在同一个事务中执行相同的查询，却得到了不同的结果集，就像"幻影"一样多出了一条记录。

问题类型 原因 典型场景 后果
丢失修改 多个事务同时修改同一数据 库存更新、余额修改 部分修改被覆盖丢失
脏读 读取到未提交的数据 读取事务中的中间状态 基于无效数据做出决策
不可重复读 同一事务中多次读取结果不同 数据验证、统计计算 事务内部数据不一致
幻读 结果集中记录数量变化 范围查询、条件统计 结果集不一致

12.2 事务的隔离级别 必考

为了防止数据不一致性，SQL标准定义了四种事务隔离级别，以在并发性和数据一致性之间进行权衡。隔离级别越高，事务的隔离性越强，数据一致性越有保障，但系统的并发性能和效率会随之下降。

就像给事务提供不同的"保护罩"，保护罩越厚，越安全，但同时也会限制事务的行动自由（影响效率）。

四类隔离级别由低到高分别是：读未提交 (READ UNCOMMITTED)、读已提交 (READ COMMITTED)、可重复读 (REPEATABLE READ)、可串行化 (SERIALIZABLE)。

四类隔离级别与不一致性问题的关系：

事务隔离级别与数据不一致性问题

隔离级别 丢失修改 脏读 不可重复读 幻读
读未提交 否 (No) 是 (Yes) 是 (Yes) 是 (Yes)
读已提交 否 (No) 否 (No) 是 (Yes) 是 (Yes)
可重复读 否 (No) 否 (No) 否 (No) 是 (Yes)
可串行化 否 (No) 否 (No) 否 (No) 否 (No)

上表中，"是"表示该隔离级别下可能出现该不一致性问题，"否"表示不会出现。 可见，可串行化是最高的隔离级别，能避免所有三类不一致性（包括幻读），因为它强制事务串行执行。而读未提交隔离级别最低，效率最高，但可能出现所有问题。

隔离级别使用场景

  • 读未提交：仅用于临时数据分析，对数据准确性要求不高的场景
  • 读已提交：大多数应用场景（默认级别），如银行账户余额查询
  • 可重复读：需要事务内数据一致的场景，如对账、报表生成
  • 可串行化：对数据一致性要求极高的场景，如金融交易、库存管理

隔离级别的选择： 了解

事务隔离级别并不是越高越好，应根据应用的特点和需求选择合适的隔离级别。例如，对于需要高并发的统计报表（即使读到少量"脏数据"对结果影响不大），可以选择较低的隔离级别以提高效率；而对于银行转账等对数据一致性要求极高的场景，则需要选择较高的隔离级别。

  • 目前大多数数据库（如KingBase、SQL Server、Oracle）默认的事务隔离级别是"读已提交"。
  • MySQL的默认级别是"可重复读"。

12.3 封锁 重要

什么是封锁？ 重要

封锁（Locking）是实现并发控制的一种重要技术。它要求事务在对某个数据对象（如表、行、页等）进行操作之前，先向系统发出请求，对其施加锁。一旦加锁，事务就对该数据对象拥有了一定的控制权，在事务释放其锁之前，其他事务不能对其进行特定的操作（取决于锁的类型）。

可以把锁想象成现实生活中的"门锁"。当你需要独占某个房间（数据对象）时，你先把它锁起来，别人就不能随便进来了。当你用完后，再把锁打开，让别人可以使用。

基本封锁类型 必考

数据库中最基本的两种封锁类型是：

  • 1. 排它型锁 (Exclusive Locks, 简记为 X 锁)：

    若事务T对数据对象A加上X锁，则只允许T读取和修改A。在T释放X锁之前，任何其他事务都不能再对A加任何类型的锁（无论是X锁还是S锁）。

    X锁是"独占锁"或"写锁"。一旦有人（事务）对数据加了X锁，其他人就都不能再碰这个数据了，无论是读还是写，必须等它释放。这确保了修改数据时的唯一性。

    X锁使用示例

    事务T1：

    BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE; -- 加X锁
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

    T1执行期间，其他事务无法读取或修改id=1的账户数据，直到T1提交释放锁。

  • 2. 共享型锁 (Share Locks, 简记为 S 锁)：

    若事务T对数据对象A加上S锁，则只允许T读取A。在T释放S锁之前，其他事务可以对A再加S锁（允许多个事务共享读），但不能加X锁（不能修改）。

    S锁是"共享锁"或"读锁"。允许多个人（事务）同时阅读一份资料（数据），但任何人都不能在阅读期间修改这份资料。只有当所有阅读者都离开后，才能允许修改。

    S锁使用示例

    事务T1：

    BEGIN;
SELECT * FROM products WHERE category = '电子' LOCK IN SHARE MODE; -- 加S锁
-- 读取产品数据...
COMMIT;

    T1执行期间，其他事务也可以加S锁读取相同产品数据，但无法修改这些数据。

锁的相容矩阵 必考

锁的相容性决定了在同一数据对象上，不同事务可以同时持有的锁类型。如果两种锁是相容的，则可以并发执行；如果不相容，则一个事务必须等待另一个事务释放锁。

就像"红绿灯"，告诉你哪些操作可以同时进行，哪些必须排队。

基本锁类型相容矩阵

请求方\被占用方 无锁 S锁 (共享) X锁 (排他)
S锁 (共享) Y Y N
X锁 (排他) Y N N

Y = Yes (相容)，N = No (不相容)
这个矩阵表明：
- 多个事务可以同时对同一数据对象加 S 锁 (共享读)。
- 任何事务要加 X 锁时，必须等待其他所有锁（S锁和X锁）释放。

锁相容性快速记忆

  • S锁之间是相容的（多个读操作可以同时进行）
  • S锁和X锁不相容（读时不能写，写时不能读）
  • X锁之间不相容（同一时间只能有一个写操作）
  • X锁与其他任何锁都不相容（写操作需要完全独占）

12.4 封锁协议 重要

只靠基本封锁（S锁和X锁）并不能解决所有并发问题。DBMS需要一套规则来指导事务如何申请和释放锁，以确保并发操作的正确性。这套规则就是封锁协议。

就像光有锁（S/X锁）还不够，还得有"使用说明书"和"规矩"，告诉大家什么时候能上锁，什么时候能开锁，才能真正避免混乱。

1. 1级封锁协议 了解

  • 事务T在修改数据R之前必须对其加X锁，直到事务结束才释放。
  • 可避免： 丢失修改。
  • 不能避免： 脏读和不可重复读。

2. 2级封锁协议 了解

  • 在1级封锁协议的基础上增加：事务T在读取数据R之前必须对其加S锁，读完即可释放S锁。
  • 可避免： 丢失修改、脏读。
  • 不能避免： 不可重复读和幻读。

3. 3级封锁协议 了解

  • 在2级封锁协议的基础上增加：事务T在读取数据R之前必须对其加S锁，直到事务结束才释放。
  • 可避免： 丢失修改、脏读、不可重复读。
  • 不能避免： 幻读。
封锁协议 加锁规则 解决的问题 未解决的问题
1级封锁协议 写前加X锁，事务结束释放 丢失修改 脏读、不可重复读
2级封锁协议 读前加S锁，读完释放；写前加X锁，事务结束释放 丢失修改、脏读 不可重复读、幻读
3级封锁协议 读前加S锁，事务结束释放；写前加X锁，事务结束释放 丢失修改、脏读、不可重复读 幻读

12.5 活锁和死锁 重要

1. 活锁 (Livelock) 了解

活锁是指事务T1请求封锁，但事务T2、T3等一系列事务持续请求并获得封锁，导致T1一直无法获得所需封锁而永远处于等待状态，虽然T1没有被阻塞，但它永远无法完成。

想象一下：你（T1）想从一扇门进去，但有很多人（T2, T3...）不停地插队先进去。虽然门没锁死，你也在努力尝试，但因为总有人插队，你永远也进不去。

解决方法： 采用"先来先服务"的公平策略，避免饥饿（starvation）。

2. 死锁 (Deadlock) 必考

死锁是指两个或多个事务在执行过程中，因互相请求对方已持有的锁而造成的一种无限期等待的僵局状态。

最经典的例子是"资源交叉占用"：事务A拿着资源X等着资源Y，而事务B拿着资源Y等着资源X。双方都在等对方释放资源，谁也无法继续，形成僵局。

死锁的产生：

通常由于以下条件同时满足：

  • 互斥条件： 资源不能共享。
  • 请求和保持条件： 事务在持有某些资源的同时，又请求新的资源。
  • 不剥夺条件： 资源只能被持有者自愿释放。
  • 环路等待条件： 存在一个等待资源的循环链。

死锁示意图

事务 T1
获得 A 的锁
请求 B 的锁
事务 T2
获得 B 的锁
请求 A 的锁
T1 等待 B，T2 等待 A，形成循环等待，进入死锁！

死锁示例代码

-- 事务T1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- 锁住账户1
-- 此时T1持有账户1的锁，请求账户2的锁
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 事务T2 (与T1并发执行)
BEGIN;
UPDATE accounts SET balance = balance - 200 WHERE id = 2; -- 锁住账户2
-- 此时T2持有账户2的锁，请求账户1的锁
UPDATE accounts SET balance = balance + 200 WHERE id = 1;

T1持有账户1的锁并等待账户2的锁，T2持有账户2的锁并等待账户1的锁，形成死锁循环。

死锁的解决方法： 了解

解决死锁主要有三种方法：

  • 死锁预防： 破坏死锁产生的四个必要条件之一。例如，一次封锁法（事务必须一次性申请所有需要的锁）、顺序封锁法（规定所有事务按固定顺序申请锁）。
  • 死锁检测： 允许死锁发生，但系统会周期性地检查是否存在死锁（例如，通过构建等待图），一旦检测到死锁，就进入死锁解除阶段。
  • 死锁解除： 当检测到死锁时，选择一个或多个死锁事务作为"牺牲品"（代价最小的事务），强制其回滚，释放锁，从而打破僵局。
解决方法 机制 优点 缺点
死锁预防 破坏死锁必要条件 完全避免死锁发生 降低并发度，实现复杂
死锁检测 定期检测死锁存在 不影响正常事务执行 检测开销大，可能遗漏
死锁解除 回滚部分事务解除死锁 实现相对简单 导致部分事务失败

12.6 并发调度的可串行性 重要

1. 调度 (Schedule) 了解

调度是指并发事务的并发执行次序。DBMS并发控制的主要任务就是对并发操作进行正确调度，保证事务的隔离性和数据库的一致性。

2. 可串行化 (Serializable) 调度 必考

可串行化调度是指：多个事务的并发执行是正确的，当且仅当其结果与这些事务的某一个串行执行结果相同。

可串行性是并发事务正确调度的最高准则。这意味着，即使事务是并发执行的，从最终结果来看，它们就像是串行地一个接一个执行完成的，确保了数据的一致性。

可串行化调度示例

假设有两个事务：

T1: R(A), W(A)

T2: R(B), W(B)

并发调度：R1(A), R2(B), W1(A), W2(B) 是可串行化的，因为它等价于先执行T1再执行T2

虽然T1和T2的操作交叉执行，但最终结果与串行执行T1→T2的结果相同。

3. 冲突可串行化 (Conflict Serializable) 调度 了解

如果一个调度可以通过交换不冲突的操作对（即不涉及同一数据的读写操作）转换为一个串行调度，那么它就是冲突可串行化调度。

  • 冲突操作： 针对同一数据项的读-写、写-读、写-写操作。
  • 冲突可串行化是可串行化的一个充分条件，但不是必要条件。 （即，冲突可串行化调度一定是可串行化调度，但可串行化调度不一定是冲突可串行化调度）

12.7 两段锁协议 (Two-Phase Locking Protocol, 2PL) 必考

定义 必考

两段锁协议 (2PL) 是一个广泛使用的并发控制策略，它将事务的锁操作分为两个阶段：

  • 1. 扩展阶段 (Growing Phase)：

    事务可以申请新的锁，但不能释放任何已持有的锁。

    就像"只进不出"：你可以不断地拿新钥匙（申请锁），但不能把已经拿到的钥匙（持有的锁）还回去。

  • 2. 收缩阶段 (Shrinking Phase)：

    事务可以释放已持有的锁，但不能再申请新的锁。

    就像"只出不进"：你可以不断地还钥匙（释放锁），但不能再拿新钥匙了。

事务必须在提交或回滚后才能释放所有锁，且一旦进入收缩阶段，就不能再回到扩展阶段。

两段锁协议示例

事务T1执行流程：

  1. 申请数据A的S锁（扩展阶段）
  2. 读取数据A
  3. 申请数据B的X锁（扩展阶段）
  4. 修改数据B
  5. 释放数据A的S锁（收缩阶段）
  6. 提交事务，释放数据B的X锁（收缩阶段）

一旦T1在第5步释放了A的S锁（进入收缩阶段），就不能再申请其他锁。

两段锁协议的优点 必考

遵循两段锁协议的并发调度都是可串行化调度。 这是2PL最重要的性质。

这意味着只要所有事务都严格遵守这个"先拿再放"的规矩，那么无论它们怎么交叉执行，最终的结果都一定和它们串行执行的结果一样，从而保证了数据库的一致性。

两段锁协议的缺点 了解

  • 可能产生死锁： 尽管2PL保证了可串行性，但它不能避免死锁。例如，事务T1持有A的X锁并请求B的X锁，同时T2持有B的X锁并请求A的X锁，就会导致死锁。
  • 降低并发度： 由于事务可能长时间持有锁（尤其是直到提交才释放），这会限制其他事务对数据的访问，从而降低系统的并发度。

12.8 封锁的粒度 (Granularity of Locking) 重要

封锁粒度是指并发控制过程中可锁定的数据单元大小，它可以是数据库、表、页（数据块）、行（记录）甚至更小的字段。

这就像"借书"：你可以借一整套丛书（数据库粒度大），也可以只借一本书（表），也可以只借书中的一页（页），甚至只借书中的一句话（行或字段）。

  • 粒度大（如数据库、表级锁）：

    优点是管理开销小，因为需要管理的锁数量少。缺点是并发度低，因为一旦锁定了整个大对象，其他事务就无法访问其中的任何小部分。

  • 粒度小（如行级锁、字段级锁）：

    优点是并发度高，因为可以更精细地控制锁定范围，允许多个事务同时访问同一大对象中的不同小部分。缺点是管理开销大，因为需要管理的锁数量多，系统用于锁管理的时间和空间资源增加。

选择合适的封锁粒度是提高数据库性能的关键。 DBMS通常采用多粒度封锁 (Multiple Granularity Locking) 来兼顾并发度和开销。

封锁粒度 锁定对象 并发度 系统开销 适用场景
数据库级 整个数据库 最低 最小 数据库备份/恢复
表级 整个表 低 小 批量数据操作
页级 数据页（块） 中 中 传统数据库系统
行级 单行记录 高 大 OLTP系统（默认）
字段级 单个字段 最高 最大 特殊应用场景

*12.9 其他并发控制机制 了解

除了封锁，还有其他一些并发控制方法，它们在特定场景下有其优势。

1. 时间戳 (Timestamp) 方法 了解

为每个事务分配一个唯一的时间戳，并为每个数据项维护读时间戳和写时间戳。事务在执行操作前，根据时间戳和数据项的时间戳来判断是否允许操作。如果发生冲突，就回滚冲突的事务。这种方法不会发生死锁，但可能会导致更多的事务回滚。

时间戳方法示例

事务T1 (TS=100) 尝试读取数据A

数据A的写时间戳(WTS)=90

因为100 > 90，允许读取，并更新A的读时间戳为100

事务T2 (TS=95) 尝试写数据A

因为95 < 100（A的读时间戳），回滚T2

2. 乐观方法 (Optimistic Scheduling) 了解

假设事务之间冲突的可能性很小，因此事务在执行过程中不加锁。事务在提交之前进行验证，检查是否与其他并发事务发生冲突。如果发生冲突，则回滚当前事务。这种方法适合冲突较少的应用场景，可以实现较高的并发度，但在冲突频繁时效率会降低。

3. 多版本并发控制 (Multi-Version Concurrency Control, MVCC) 了解

MVCC为每个被修改的数据项维护多个版本。当一个事务读取数据时，它读取的是数据的一个旧版本，而不是当前正在被修改的版本。这样，读操作和写操作之间不会互相阻塞，大大提高了读操作的并发性。写操作会创建新的数据版本。这种机制广泛应用于现代数据库系统（如PostgreSQL、Oracle、MySQL的InnoDB）。

就像给数据拍照，每次修改都生成一张新照片。读取的人看到的是旧照片，写的人修改的是新照片，互不影响。

MVCC示例

初始状态：数据X=10（版本V1）

事务T1开始，读取X=10（V1）

事务T2修改X=20（创建新版本V2）

事务T1再次读取X，仍然得到10（V1）

事务T2提交后，新事务读取X得到20（V2）

并发控制方法比较

方法 机制 优点 缺点 适用场景
封锁机制 加锁控制访问权限 保证强一致性 可能死锁，开销大 传统OLTP系统
时间戳 基于时间戳顺序控制 避免死锁 回滚多，实现复杂 分布式系统
乐观控制 提交时验证冲突 高并发，无锁 冲突多时效率低 冲突少的系统
MVCC 维护多个数据版本 读写不冲突 存储开销大 读多写少系统
